Rays second simplification pass

This is the follow-up to the first plan, whose 63 items are done. A second audit across all 51 crates found 58 changes. The goal is a Rust engine that is fast, compact and does not allocate in steady state, with no OCaml compatibility left. Finished items from the first plan are not proposed again.

Rule for this pass: OCaml compatibility is gone. Nothing has to keep OCaml's sort order, its 63-bit hashes, its float printing or its random seeds. Goldens are Rust-owned snapshots: when a change alters output on purpose, its commit regenerates the affected goldens. They never block a performance change. Four things remain invariant:
  • Lisp semantics as written in specification/; the spec is edited in the same commit when a change alters it.
  • Determinism.
  • Exact equality between sequential and parallel runs.
  • Identical results on macOS and Windows.

The edit-and-rebuild loop is already fast. The bigger costs are the same crates being compiled again under different feature sets, too many test binaries to link, and per-call work in the Metal and evaluator hot paths. Line savings come mostly from the Metal layering and from helpers that the port copied into many files.

The 63-bit integers are not fully gone. Wave I removed them from the language. They remain in three places:
  • the settings parser, which is a bug (X2);
  • OCaml max_int/min_int caps and sentinels in about a dozen runtime places (X2);
  • the hash and random functions, through 29 wrap_int63 calls. These were kept only to match OCaml seeds; Z5 replaces them.

Order

  1. X1–X5 first, each with its regression. X6 goes with G.
  2. B1, B2, B3, B5, B6: one commit each, no behaviour change. Then measure the switch between cargo build and cargo t, and the flow_sop run time.
  3. B4 crate by crate. Case names must match before and after.
  4. A1–A4, then B8.
  5. D1–D12 in parallel by crate, at most two building agents at a time.
  6. Z0 right after B, so every later commit lowers a guard.
  7. R1–R10, then Z1, Z2, Z9 and Z10, to drive idle frames and warm cooks to 0 allocations.
  8. Z5, Z6 and Z8, which remove OCaml behaviour, each with its spec edit and goldens regenerated in the same commit.
  9. Z3, Z4 and Z7, the large performance changes, each measured before and after with bench_core, frame times and cargo-timings.
  10. G1 → G2 → G3 → G4 one after another, then G5, X6, G6 and G7. Each step is checked on the Windows box.
  11. B7 after cargo-timings confirms the critical path. R11 is documented under R11 → Z7.

Every step follows AGENTS.md: a focused cargo t, git diff --check, gate deps for any boundary edit, and one commit per item. When a change alters output on purpose, its commit regenerates the affected goldens and says so in the message. The workspace and native editor qualification runs at the end on both platforms. No deadline is raised and no assertion is weakened.

Runbook

  • One stage per commit named for its ID (X1, B3, …). While editing: cargo check -p <crate>; then cargo t -p on touched crates and consumers; cargo run -p gate -- deps after boundary edits.
  • Parallel work: at most two building agents on distinct crates (wave D); wave B items are sequential one-commit steps unless noted.
  • Allocation claims: measured with mem_sys guards and real frames; Z0 limits only ever lowered.
  • GPU wave G: check Windows Vulkan after each of G1–G4; keep Metal qualification on macOS.
  • Qualification at the end: full workspace suite and native editor limits on both platforms; no raised deadlines.

R11 → Z7 (value-dependent lowering)

The first pass deferred parameter-independent lowering as R11. This pass folds that work into Z7: lower each residual body once keyed by term, site and binding shape; hash-cons residual_id; bind values at cook time. Success: Orrery frames lower 0 times after warm-up; flow_sop stays under its cap. High risk — measure with frame timers before closing.

Checked and kept

Pipeline

  • Term → Core → Region: three real tiers, each running something different.
  • Shader printers: MSL, WGSL, SPIR-V and JS already share kernel_layout.
  • Parser and packed engine: one parser; one CPU engine since D4.

Editor

  • Intent enums between pane and document: they are the boundary that keeps UI from mutating the document.
  • Splitting rays_editor: a 0.40 s touch-check does not justify it. B1, B8 and R8 recover more.
  • Long functions: splitting them removes no code.
  • Injected prepare/draw closures: six tests replace them.

Runtime and geometry

  • Type erasure in lru/mem, the worker pool, vendored libm: kept on purpose. The vendored libm is what makes results identical across platforms.
  • scene_command → render_ir → draw: each step does real work.
  • Code bloat from generics: not a problem today. Z3 adds generics only at measured kernel entry points.

Method: five read-only audits by area (rdk, Flow pipeline, editor/UI, runtime/GPU, flow_sop with the test layout), spot-checked against the source. Rebuild times were measured on the M-series dev box. Other timings come from target/t-times.tsv and cargo-timings. Line estimates come from wc over each duplicate family.
